Block Transform Coding & JPEG

Every idea from this entire unit converges here. Frequency-domain thinking (Sections 1–5), the DCT's superior energy compaction (Section 7), entropy coding (Section 9), and run-length coding (Section 10) all combine into one concrete, ubiquitous standard: JPEG. This section is where the whole unit pays off.

Deck 11, slide 2 — section divider: "Lecture 11: Block Transform Techniques."

11.1 · Block transform coding: the general recipe

Rather than transforming an entire image at once (as Sections 1–5's whole-image DFT filtering did), block transform coding divides the image into small, non-overlapping n×n blocks and transforms each one independently: forward transform → quantizer → symbol encoder, with the decoder running the mirror-image pipeline in reverse (symbol decoder → inverse transform → reassemble the blocks).

The goal of the transform step is exactly Section 6.4's energy-compaction and decorrelation properties, now stated as the explicit design objective: decorrelate each block's pixels, and pack as much information as possible into the fewest coefficients — so that quantization (discarding or coarsening the least-informative coefficients) does the least possible visible damage.

The counterintuitive part Working block-by-block instead of on the whole image at once introduces a defect that whole-image transform coding never had: a blocking artifact — visible discontinuities right at block boundaries, because each block is quantized and reconstructed with zero knowledge of its neighbors. This is the direct cost of the locality traded for in Section 7.4's DWT discussion, but here applied to a fixed-size grid rather than a multiresolution pyramid — and it's precisely why the choice of block size (Section 11.2) and transform (Section 11.1's "adaptive vs. non-adaptive" distinction) matters so much in practice.

Truncating the transform with a masking function

Ĝ = Σu=0n−1 Σv=0n−1 χ(u,v)·T(u,v)·Suv     χ(u,v) = 0 if T(u,v) meets a truncation rule, else 1

This is Section 6.4's basis-image sum (Ĝ built from a weighted stack of basis images Suv), with one new ingredient: the masking function χ(u,v) is a per-coefficient on/off switch that zeroes out coefficients meeting some "not worth keeping" criterion — the formal machinery behind every energy-compaction demo run so far in this unit (Section 1.5's DFT truncation, Section 7.2's DCT-coefficient truncation).

11.2 · Choosing the block size

Block size n is a genuine trade-off, not a free parameter: larger blocks generally improve both compression and reconstruction error, but cost more computation per block. The reconstruction-error chart makes the DCT's advantage (first demonstrated qualitatively in Section 7.2) numerically concrete: at every subimage size, the DCT curve sits well below both the DFT and the Walsh-Hadamard Transform (WHT, a matrix transform built from ±1 entries rather than sinusoids) — confirming with real RMSE numbers that the DCT compacts more energy per coefficient than its Fourier-family competitors, at every block size tested.

n is conventionally restricted to a power of 2, purely for computational convenience — it lets the same fast, recursive transform algorithms (the FFT-style structure discussed in Section 1.4) apply directly to each block. 8×8 and 16×16 are called out as the most popular choices in practice — 8×8 is exactly the block size JPEG itself uses (Section 11.4).

The visual comparison confirms the same story: keeping a fixed 25% of DCT coefficients, larger subimages (2×2 → 4×4 → 8×8) recover progressively sharper, more faithful detail from the same coefficient budget.

11.3 · Bit allocation: deciding which coefficients survive

Bit allocation is the umbrella term for the full truncate/quantize/code decision made per sub-image. Two masking strategies for choosing which coefficients to keep:

  • Zonal coding — keep coefficients based on maximum variance, using one fixed mask (zone) applied identically to every sub-image in the picture, regardless of that particular block's actual content.
  • Threshold coding — keep coefficients based on maximum magnitude, within that specific block — inherently adaptive, since which coefficients survive can differ from block to block.

A direct, controlled comparison — both methods discarding the identical 87.5% of DCT coefficients per 8×8 block — shows threshold coding winning decisively: RMSE 4.5 versus zonal coding's RMSE 6.5. The difference-image panels make the reason visible: threshold coding's errors cluster tightly around genuine high-detail regions (hair, hat brim), while zonal coding's fixed, content-blind mask throws away coefficients that happened to matter a lot in some blocks and very little in others.

Filling a gap the slide leaves implicit This result is a direct, concrete instance of Section 6's "adaptive vs. non-adaptive" distinction from Section 11.1: zonal coding is the non-adaptive case (one rule for every block, everywhere), threshold coding is the adaptive case (the rule reacts to each block's own actual content). Adaptive methods essentially always win on reconstruction fidelity for the same coefficient budget — the cost is needing to additionally signal, per block, which coefficients survived (since it now varies block to block), which is exactly why the deck notes threshold coding needs run-length coding (Section 10.1) as an overhead-reduction partner: RLE cheaply encodes "which positions were kept" as a sequence of skip-lengths rather than one flag bit per coefficient.
Deck 11, slide 10 — three ways to threshold: a single global threshold, a per-subimage threshold (N-largest coding), or a threshold varied by each coefficient's location.

Thresholding and quantization combine into a single step: a normalization matrix Z(u,v) divides each raw DCT coefficient before rounding, so which coefficients survive (large Z → aggressively shrunk toward zero) and how much precision a surviving coefficient keeps are controlled by one matrix. This Z matrix is exactly what Section 11.4 calls the JPEG "quantization table."

11.4 · JPEG: block transform coding, as an actual standard

JPEG (Joint Photographic Experts Group) fixes every free parameter from Sections 11.1–11.3 into one concrete, universally-adopted recipe: 8×8 blocks, the DCT (chosen specifically for its blocking-artifact minimization and energy compaction — Section 7.2's derivation directly justifies this choice), and threshold coding via quantization. The encoder and decoder pipelines are exact mirror images of each other, exactly as Section 11.1's general block-transform-coding diagram predicted.

Step 1 (optional) — color transform and chroma downsampling

RGB is converted to a luminance/chrominance space (Y for brightness, U and V for color), because the human eye is far more sensitive to changes in brightness than in color. This lets JPEG throw away chroma resolution the eye won't miss: 4:1:1 subsampling keeps all 4 Y (luminance) samples in a 2×2 pixel block but averages down to just 1 U and 1 V sample for that whole block — already a 2:1 reduction in total data before the DCT step even begins, exploiting the psychovisual redundancy named back in Section 8.2.

Steps 2–3 — 8×8 blocks, DCT

The image (per color channel) is tiled into 8×8 blocks, and each block's 64 pixel values become 64 DCT coefficients — exactly the single-block DCT demonstrated with real numbers in Section 7.2. As established there, one DC coefficient (top-left, the block's average) plus a small handful of low-frequency AC coefficients carry almost all of the block's energy.

Step 4 — quantization: where the actual lossy compression happens

The DCT itself is lossless (up to floating-point rounding) — reversing it recovers the exact original block. All of JPEG's controllable, dial-a-quality lossiness happens in this one step: every coefficient is divided by an integer from a quantization table and rounded. Because the human eye is far less sensitive to high spatial frequencies (Section 4's whole premise about what high-pass content even represents), the quantization table divides high-frequency coefficients by larger numbers than low-frequency ones — coarser quantization exactly where it's least likely to be noticed. This single table, tunable to trade file size against visual quality, is the "JPEG quality" slider — and it must be stored alongside the compressed data so the decoder knows how to reverse it.

Steps 5–7 — zigzag order, RLE, Huffman

Reading the quantized 8×8 coefficient grid in a diagonal zigzag (rather than row-by-row) puts low frequencies first and high frequencies last — and because quantization has already rounded most high-frequency coefficients down to exactly zero, the zigzag ordering turns them into one long trailing run of zeros. That's a deliberate setup for Section 10.1's run-length coding to work as well as possible: RLE shines precisely on long, uniform runs, and the zigzag reordering manufactures exactly that. The run-length symbols are then Huffman-coded (Section 9), using the exact same "short codes for frequent symbols" logic — here, "a zero-run of a common length" is simply a very frequent symbol.

11.5 · JPEG-2000: the wavelet-based successor

JPEG-2000 swaps out the DCT for the DWT (Section 7.4) and bit-plane coding (Section 10.4) for its core transform-and-code steps, gaining several practical advantages that follow directly from properties already established earlier in this unit: no blocking artifact (the wavelet transform isn't confined to a fixed 8×8 grid the way JPEG's DCT is — Section 11.1's core defect simply doesn't arise the same way); much better low-bitrate quality (the DWT's multiresolution structure degrades by getting progressively blurrier, not blockier, as Section 7.4's LL-only reconstruction demonstrated); and new features unavailable to block-based JPEG, like region-of-interest coding and true random access into the compressed bitstream.

At an extremely aggressive 0.125 bits per pixel, the difference is stark: JPEG's DCT blocks have completely collapsed into a visible 8×8 grid of flat tiles, while JPEG-2000's wavelet-coded result remains soft and blurry but structurally coherent — no grid artifact anywhere. This single comparison image is the clearest possible payoff of Section 7.4's honest DWT-vs-DCT trade-off table: DWT's computational cost buys real, visible robustness at the low-bitrate extreme, exactly where JPEG's blocking artifact is at its worst.
