8.1 · Why compression matters, in real numbers

The slide's own back-of-envelope calculation is worth keeping, because it makes the stakes concrete rather than abstract: a 2-hour movie at typical broadcast bitrate works out to roughly 224 GB uncompressed. Fitting that onto a single 8.5 GB dual-layer DVD requires compressing every single frame by a factor of about 26.3× — and HD content, at a much higher native resolution, needs even more. Compression isn't an optional efficiency tweak here; without it, the storage and bandwidth most image and video applications assume simply would not exist.

Data vs. information — a distinction worth being precise about

Data is the physical representation (bits, symbols); information is what those bits actually convey. The same information can always be represented by different amounts of data — and compression is specifically the search for a smaller amount of data that still conveys (all or most of) the same information. Whenever a representation uses more data than the information it carries strictly requires, that excess is called redundancy — and it's the redundancy, not the information, that compression removes.

8.2 · Three kinds of redundancy in image data

Deck 8, slide 9 — "what can we compress?": coding redundancy exists whenever gray-level codes ignore event probabilities; goals: remove redundancy, reduce irrelevance.

Every compression technique in this unit works by targeting one (or more) of exactly three redundancy types:

  1. Coding redundancy — using more bits per gray level than the actual statistics of the image require. A fixed 8-bit code spends the same 8 bits on a gray level that occurs constantly as on one that occurs almost never — wasteful whenever gray-level probabilities are uneven, which they almost always are (illustrated by the star-shaped test pattern, whose flat, sharply-bounded regions can be losslessly described far more economically than a naive per-pixel code would).
  2. Spatial and temporal redundancy — neighboring pixels tend to be similar (spatial), and corresponding pixels in nearby video frames tend to be similar (temporal). The striped test pattern makes this vivid: every row is identical to the row above it, so storing each row independently repeats information that a smarter scheme would only need to store once.
  3. Irrelevant information — detail present in the data but essentially invisible or unimportant to a human viewer (the third, nearly-flat gray panel). This is the redundancy category that lossy compression is specifically willing to sacrifice, on the bet that a viewer won't notice or won't care.
Filling a gap the slide leaves implicit Notice how each redundancy type maps onto a section of this unit: coding redundancy is exactly what Section 9's Huffman coding targets (short codes for common symbols, long codes for rare ones — precisely "codes not selected to take advantage of the probabilities of the events," which the deck flags directly on the next slide); spatial redundancy is what Sections 6–7's transforms and Section 10's run-length coding exploit (a smooth region transforms into a few large coefficients, or a repeated run compresses into one count); and irrelevant/psychovisual information is what a lossy quantizer (Section 8.4 below) throws away on purpose. Nothing in Sections 9–11 is really a new idea — it's this same three-way taxonomy, applied with different tools.

Coding redundancy, made concrete: the actual entropy of this image

The slide states that coding redundancy exists whenever gray levels are not equally probable. Measuring this directly on sample.png's own 256-level grayscale histogram gives a first-order entropy of 6.876 bits/pixel — meaningfully below the naive 8 bits/pixel a fixed-length code spends on every pixel. That gap (8 − 6.876 = 1.124 bits/pixel) is coding redundancy sitting in the raw file, before any transform or prediction step is even applied — and it upper-bounds how much a pure entropy coder (like Section 9's Huffman code) can save on this image without changing a single pixel value. (See Section 9 for exactly how a real code gets built to close most of that gap.)

8.3 · Measuring how well a scheme compresses

CR = n₁ / n₂

The compression ratio is simply the size before compression divided by the size after — a CR of 10 means the original data used 10 units for every 1 unit the compressed version needs.

RD = 1 − 1/CR

Relative data redundancy reframes the same number as a fraction: at CR = 10, RD = 0.9, meaning 90% of the original representation's bits were redundant — genuinely unnecessary to preserve the same information (for lossless schemes) or the same acceptable fidelity (for lossy ones).

Fidelity: how do you judge what was lost?

Compression ratio alone says nothing about quality — a scheme could hit a huge ratio simply by discarding the image entirely. Fidelity criteria quantify what was lost, in two flavors:

  • Objective — a mathematical function of the input and output, needing no human judgment at all (e.g. RMS error between original and reconstructed images).
  • Subjective — averaged human ratings, since a numerically small error can still be visually jarring (or vice versa) depending on where in the image it falls.

The Television Allocations Study Organization's 6-point rating scale (Excellent → Unusable) is a concrete example of subjective fidelity in practice — a reminder that "good enough" compression is ultimately defined by how real viewers judge the result, not only by an error formula.

This is the exact trade-off named back in Section 8.2's "irrelevant information" redundancy type: lossy compression is precisely the decision to also discard that third redundancy category, on top of the coding and spatial redundancy a lossless scheme already removes. Sections 9–10 (Huffman, RLE, bit-plane, CCITT) are lossless; Section 11 (block transform coding, JPEG) is lossy.

8.5 · The general image compression pipeline

Every compression system in this unit — however different its internals — is an instance of the same compress/store-or-transmit/decompress loop: f(x,y) goes into a compressor, the compressed bits are stored or transmitted, and a decompressor later reconstructs an approximation f̂(x,y) of the original (identical to f(x,y) for a lossless scheme, an approximation for a lossy one).

Inside the encoder: three independent stages

Deck 8, slide 26 — the symbol encoder in detail: reversible, shortest codewords to the most frequent quantizer outputs; its completion means all three redundancy types have been addressed.
  1. Mapper — transforms the image into a format that exposes and reduces spatial/temporal redundancy (e.g. a DCT/DWT transform, or run-length coding). Reversible; may or may not shrink the data by itself.
  2. Quantizer — discards irrelevant (psychovisual) information to reduce the data further. Irreversible — this is the one stage that must be skipped entirely for error-free (lossless) compression.
  3. Symbol encoder — assigns a fixed- or variable-length code to the quantizer's output, giving the shortest codes to the most frequent values (directly attacking coding redundancy). Reversible. This is exactly where Section 9's Huffman coding operates.
The counterintuitive part The decoder's block diagram is deliberately missing an "inverse quantizer." That's not an oversight — the slide states it directly: quantization is irreversible, so there is nothing for a decoder to invert. A lossy decoder can only reverse the mapper and the symbol coder; whatever precision the quantizer discarded is genuinely gone, permanently, the moment it happens. This is the single structural fact that separates "lossy" from "lossless" at the architecture level, not just at the philosophical level of "some quality was lost."

Source coding vs. channel coding — a distinction worth not confusing

Everything above (mapper, quantizer, symbol coder) is source coding — squeezing out redundancy that was already in the data. A full transmission system typically adds a second, entirely separate stage afterward: channel coding, which deliberately adds back controlled, structured redundancy (e.g. a Hamming code) to protect the now-compressed data against transmission errors. It's worth being precise about the direction of each step: source coding removes redundancy to shrink data; channel coding adds a different, engineered kind of redundancy back in to make that shrunk data robust to noise. The two are not in tension — they operate on the data in sequence, for entirely different reasons.
