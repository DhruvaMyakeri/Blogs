Huffman Coding

Section 8.2 defined coding redundancy as spending equal-length codes on symbols that occur with wildly unequal probability. Huffman coding is the concrete algorithm that removes exactly that redundancy — provably optimally, for a code built one symbol at a time.

9.1 · Entropy: the theoretical floor on code length

Before building any code, it helps to know the best any code could possibly do. Entropy measures how unpredictable a source is: a source that always emits the same symbol has zero entropy (nothing to learn from seeing the next symbol); a source where every symbol is equally likely has maximum entropy (every next symbol is a genuine surprise). The soup-throwing illustration makes this visceral — soup that always lands in the bowl (low entropy, one predictable location) versus soup scattered uniformly across the whole dining room (high entropy, no way to guess where the next bit lands).

Deck 9, slide 7 — the formal information-theory source for the I(E) and η=H(S) formulas below.
I(E) = log(1/P(E)) = −log P(E)      η = H(S) = −Σi=1n pi log₂ pi

A single event E with probability P(E) carries −log P(E) bits of "surprise": a near-certain event (P close to 1) carries almost no information when it happens, while a rare event (P close to 0) carries a lot. Averaging that surprise over every symbol in the alphabet, weighted by how often each symbol actually occurs, gives the entropy η — the theoretical minimum average number of bits per symbol that any lossless code could achieve for that source. This is the number Huffman coding is trying to approach as closely as possible.

Deck 9, slide 5 — the "Barbara" differential (x-derivative) image: a more compact histogram means lower entropy than the original photo.

The camera-operator example shows entropy responding exactly the way it should: the plain photograph has entropy 7.032 bpp (close to the naive 8, since gray levels are fairly evenly spread); an edge-enhanced/local-equalized version compresses that spread into fewer effective levels, dropping entropy to 4.348 bpp; and a binary threshold — only two possible values — collapses it to just 0.976 bpp, barely above the theoretical minimum of 1 bit for a source with (roughly) two equally-likely outcomes.

9.2 · The Huffman algorithm

Huffman coding builds a prefix code — no codeword is ever the bit-string prefix of another — which is precisely what makes the code instantaneous (a decoder recognizes a complete symbol the moment it's seen, no lookahead needed) and uniquely decodable (there is never any ambiguity about where one codeword ends and the next begins). Given a set of symbols and their probabilities, Huffman's algorithm produces the prefix code with the lowest possible average length — the best any one-symbol-at-a-time code can do.

Method I: source reduction

Deck 9, slide 9 — Huffman coding is variable-length, instantaneous, uniquely-decodable block coding; used in CCITT, JBIG2, JPEG, MPEG, H.26x.
  1. Order the symbols by probability, largest to smallest.
  2. Merge the two smallest-probability symbols into one compound symbol whose probability is their sum; re-sort.
  3. Repeat until only one (probability-1) compound symbol remains.
  4. Walk the merges back in reverse, assigning a 0 and a 1 to the two branches created at each merge.

For the six-symbol source {a₂:0.4, a₆:0.3, a₁:0.1, a₄:0.1, a₃:0.06, a₅:0.04}, repeated merging collapses everything down to a single node, and reversing the process assigns progressively longer codes to progressively rarer symbols: a₂ → 1 (1 bit — the most frequent symbol gets the shortest code), all the way down to a₅ → 01011 (5 bits — the rarest symbol gets the longest code). The average code length here works out to Lavg = Σ l(rk)p(rk) = 2.2 bits/symbol — well under the ⌈log₂6⌉ = 3 bits a fixed-length code would need for 6 symbols.

The counterintuitive part Notice the shortest code (a₂, length 1) went to the symbol with the highest probability, and the code lengths grow monotonically as probability shrinks. This is not a coincidence of this particular example — it is the entire mechanism of the algorithm: because the two rarest symbols are always merged first, they are always buried deepest in the resulting tree, and tree depth is exactly codeword length. "Frequent symbols get short codes" isn't a design goal bolted on afterward; it falls directly out of always merging the smallest two probabilities first.

Method II: building the binary tree directly (bottom-up)

This is the same algorithm viewed as tree construction rather than table reduction — and it's the version worth internalizing, since it generalizes cleanly to code (a priority queue of nodes, repeatedly popping the two smallest and pushing their merged parent back in). Working through the alphabet {C:32, D:42, E:120, K:7, L:42, M:24, U:37, Z:2}:

Step 1 sorts by frequency. Steps 2 onward repeatedly take the two lowest-frequency nodes still available (first Z:2 and K:7, merging into a weight-9 internal node) and feed the merged node back into the pool as if it were an ordinary symbol with that combined weight.

The process keeps merging the two lowest weights available at each step — (2,7)→9, then (9,24)→33, then (32,33)→65, then (37,42)→79, then (65,79)→... — climbing steadily until every symbol is absorbed into one tree rooted at the total weight, 306 (the sum of every frequency).

Labeling every left branch 0 and every right branch 1 and reading each leaf's path from the root gives the final code: E=0, U=100, D=101, L=110, C=1110, Z=111100, K=111101, M=11111. Once again, E — by far the most frequent symbol at 120 — gets the shortest possible codeword (a single bit), while Z and K, the rarest at 2 and 7, get buried 6 bits deep. The slide's own summary rule captures the whole algorithm in one sentence: a letter with high weight has low depth, and vice versa — Huffman coding is, at its core, a search for the tree with minimum weighted path length, where each leaf's contribution is its own weight times its own depth.

Worked example: encoding and decoding actual text

A second, smaller alphabet {A:17, B:12, C:12, D:27, E:32} produces the code A=00, B=010, C=011, D=10, E=11. Encoding the string "EAEBAECDEA" symbol-by-symbol via table lookup, then concatenating, gives the bitstream 1100110100011011101100. Decoding runs the identical tree in reverse: because the code is prefix-free, the decoder can walk the bitstream left to right, greedily match the shortest valid codeword at each position, and recover "EAEBAECDEA" with zero ambiguity — the practical payoff of the instantaneous/uniquely-decodable properties defined back in Section 9.2's opening.

9.3 · Applying Huffman coding to an image histogram

Everything above generalizes directly to image compression the moment the "alphabet" becomes the set of gray levels and the "probabilities" become the image's own normalized histogram — precisely the setting Section 8.2's coding-redundancy discussion was building toward.

Worked example: a real 3-bit image histogram

An image with 8 possible gray levels (3 bits/pixel, naive fixed-length coding) has the histogram shown — heavily skewed, with level 7 alone covering 60.1% of all pixels. A fixed-length code spends 3 bits on every pixel regardless, giving Lavg = 3 exactly.

Running the same merge-the-two-smallest procedure across all 8 gray levels gives the dominant level 7 a single-bit code ("0") and buries the rare levels 5 and 6 four bits deep — and the resulting average length drops to Lavg = 2.10 bits/pixel. Plugging into Section 8.3's own compression-ratio formulas:

CR = n₁/n₂ = 3/2.10 = 1.43      RD = 1 − 1/CR = (3 − 2.10)/3 = 0.3

In plain terms: simply re-coding the same gray levels — no blurring, no transform, no information discarded — losslessly shrinks this image to 70% of its original size, just by exploiting the fact that one gray level dominates the histogram. This is coding redundancy, identified in Section 8.2, actually being removed.

Worked example: computing degree of compression directly from pixel counts

A second, fully worked problem starts from a raw 6×5 pixel grid with 4 gray levels {0,1,2,3} and counts occurrences directly: P(0)=15/30=0.5, P(3)=9/30=0.3, P(2)=4/30=0.1333, P(1)=2/30=0.0667. Building the Huffman tree the same way — repeatedly merging the two smallest probabilities (0.0667 and 0.1333 merge first, then that 0.2 merges with 0.3, then that 0.5 merges with the remaining 0.5) — gives codewords 0→1, 3→01, 2→001, 1→000. The most frequent value (0, at 50% of all pixels) gets the shortest 1-bit code, exactly as the pattern predicts.
